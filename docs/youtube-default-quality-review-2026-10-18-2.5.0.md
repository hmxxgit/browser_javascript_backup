# YouTube 默认画质 2.5.0 复查与修复

日期：2026-10-18（Asia/Shanghai）。审查基线：`4354b70231c62dd68643b8b93652d1ad4db3a6a1`（2.4.0）。用户反馈：进入视频后仍有一两秒延迟才看到固定 1080P，希望进入视频时立即选择。

## 延迟来源

2.4.0 的“点击后 1 秒确认”并不会推迟画质选择本身；延迟主要来自 2.2.0 为规避 YouTube 启动控制器重置而加入的**两秒媒体稳定窗口**：

1. `probe()` 要求 `video.readyState >= 2`、`getPlayerState()` 为播放 / 暂停，并且同一媒体源连续稳定 **2000ms** 才执行首次选择。
2. 即使媒体事件到达，旧的 `schedule()` 在已有计时器时直接返回，不能把探测提前到下一轮 500ms / 1s 之外。
3. 只有主视频真正开始播放后，`noticeContentPlayback()` 才重置一次额度，但首次选择仍受上面的稳定窗口约束。

真实页面测量（Edge 155.0.4283.62，播放器 `0229cd64`，用户报告视频 `nPdqduzfI3c&t=31162s`）：媒体帧在约 4.18 秒就绪，固定画质直到约 5.3 秒才出现；设置面板打开时更晚。

## 修复

- **立即选择**：只要 `readyState >= 1` 且画质列表可用就执行；不再要求 `getPlayerState()` 为 1/2，也不再固定等待 2 秒。只保留 **250ms** 的同源检查，用于合并启动期媒体源替换。
- **通知可提前探测**：记录 `timerDue`；新的媒体 / 播放器通知如果到期时间更早，会清除旧计时器并提前探测，而不是等旧计时器。
- **启动后复查**：原生选择完成并进入 `applied` 后，在 **1.5 秒和 3 秒**各检查一次原生 Quality 摘要与画质勾选项。若 YouTube 启动控制器将其改回 Auto，重新应用固定档位；每次访问最多自动纠正 2 次，不持续与 ABR 争夺。
- **保留已有的 1 秒原生确认**：它决定何时标记 `applied` 和何时重试，但不延迟用户看到的画质变化。
- **重新应用**仍会重置 `nativeAttempts` / `menuAttempts` / 纠正次数。

## 验证

离线：

```sh
node --check youtube-default-quality.user.js
node --test tests/youtube-default-quality.test.cjs   # 127/127
npm test                                             # 146/146
```

新增 / 调整的回归：

- 媒体元数据未就绪时不消耗选择机会；就绪后 1 秒内完成一次选择。
- 早期媒体源替换在 250ms 窗口内合并，只产生一次选择。
- 原生确认的延迟应答、导航、手动固定档位、手动 Auto 在“立即选择”时仍按预期工作。
- 测试 harness 增加 `setupClock`，可把异步准备测试固定在准备中的状态，不再依赖旧的 2.5 秒初始等待。

真实页面：

- 媒体帧就绪（`videoWidth=426`）后约 **0.25 秒**触发固定选择，`getPreferredQuality()=hd1080`。
- 设置面板从 0.8 秒起保持打开：约 2 秒内画质子菜单勾选 **1080p HD**；关闭后摘要 **1080p HD**。
- 手动点击 Auto 后数秒内恢复固定 1080p HD，状态 `applied`，`manualOverride=false`。
- 页面无脚本异常；设置面板打开时不关闭、不抢焦点。

## 边界

- 250ms 的源检查不是零延迟；页面加载和播放器初始化本身的耗时无法由脚本消除。
- 移除两秒窗口后，极早的选择仍可能被启动控制器重置；脚本依靠 1 秒确认和 1.5 / 3 秒复查纠正，纠正次数有上限。若 YouTube 在 3 秒后再次重置，或原生摘要 / 勾选在复查时都不可读，脚本不会无限争夺。
- `readyState >= 1` 时选择不要求视频已播放或暂停，暂停 / 自动播放被阻止的页面也会立即设置；这与旧版“等主视频开始”的行为不同。
- 真实页面验证集中在用户报告的单个直播回放；未覆盖所有直播、广告、移动端、TV 与账号实验。内部菜单结构变化仍可能使摘要 / 勾选校验失效。
